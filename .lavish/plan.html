Technical Plan · Pre-Implementation

chatgpt-oauth — one core, every platform

A small, honest SDK that lets end users sign in with their own ChatGPT account and run OpenAI models on their subscription — across web, React Native, and native iOS/desktop. This plan is grounded in a file-by-file read of the six reference implementations and our own three apps.

verified against: loginwithchatgpt · ben-vargas · openclaw · hermes · codex-rs apps to migrate: ai-finances · calorie-tracking · music-player
The goal

Build a clean, cross-platform SDK — a ~2k-line lifecycle core plus thin adapters, never a gateway.

Everything shipped so far is fragmented: loginwithchatgpt is local-first web/Node only; ben-vargas is an AI-SDK shim with no built-in refresh-on-401; openclaw and hermes have the best engineering but welded inside a 27k-file agent OS and a Python monolith. The unbuilt ground is the web + React Native + Swift trifecta with codex app-server as a first-class transport. That gap is the reason to build.

Two things this plan changed after reading the source: (1) the app-server mode we planned to target is stamped internal-use-only in Codex's own code — so backend-api ships first and app-server is gated behind an explicit flag; (2) the refresh margin is inconsistent across every reference (60s / 120s / 300s) — we standardize on one value. Details in §5 and §10.

01

The non-negotiable: one ChatGPT identity ↔ one app user

The bug already shipped in ai-finances. The SDK's API shape must make pooling structurally impossible, not merely discouraged.

CONCRETE FAILURE shipped

ai-finances seeds one account for the whole app via CHATGPT_OAUTH_TOKENS_B64 → a single global sync_state row (PK is just key, no user_id column exists). Bob signing in overwrites Vish's bearer; Vish's next request runs against Bob's subscription while two refreshers race on one token. Tokens are stored base64, not encrypted — reversible by anyone with a DB backup.

THE FIX IN THE TYPE by shape

Every store method takes a subject derived server-side from the app session. Clients never submit a userId, a chatgpt-account-id, or a bearer. There is no global-key code path to misuse — the single-arg load() that ai-finances relied on simply does not exist in the interface.

The exact change — apps/web/lib/ai/chatgpt-oauth.ts

Left: the global-pool read that serves one operator's tokens to every visitor (chatgpt-oauth.ts:62-84). Right: subject-scoped, encrypted, no env-seed path.

03

Architecture — one lifecycle core, thin platform adapters, two transports

The core owns the token lifecycle and knows nothing about transport. Stores are keyed by subject. Transports sit behind one interface with app-server as the target and backend-api as the shipping-first fallback.

Guardrail: the auth client is never the inference client. CredentialStore has no single-arg load() — every method requires subject, so a global token pool cannot be expressed.

core

PKCE, device-code, refresh singleflight, quarantine, JWT parse. Zero platform or transport imports. This is where correctness lives.

stores

Three real adapters. Each takes subject. Web = encrypted DB row; RN = SecureStore; iOS = Keychain. Desktop (Electron/Tauri) reuses store-web or a keytar store.

transports

Both behind connect(subject): SubscriptionAI. app-server default once proven; backend-api the flagged fallback — never a silent downgrade.

04

Token lifecycle — the state machine none of our apps have

All three of our apps are missing quarantine. calorie-tracking is the only one with refresh-race protection. The core makes all of it mandatory and identical everywhere.

stateDiagram-v2
  [*] --> LoggedOut
  LoggedOut --> Authenticating: beginLogin (PKCE S256)
  Authenticating --> Active: completeLogin, store encrypted
  Active --> Refreshing: expiry-120s OR reactive 401
  Refreshing --> Active: rotate + compare-and-swap by version
  Refreshing --> Quarantined: invalid_grant / 401 / 403
  Quarantined --> Authenticating: user re-auth
  Active --> LoggedOut: logout (delete local tokens)
  Quarantined --> LoggedOut: logout

Refresh — singleflight + CAS

hermes' pattern: cheap unlocked staleness check → cross-process lock → re-read under lock → re-check → refresh. A process that loses the race sees the winner's rotated token and skips. Prevents two refreshers double-consuming a single-use refresh token. hermes auth.py:3808-3824

Quarantine — the missing piece

On invalid_grant or a bare 401/403 from the token endpoint (never on 429), mark refresh dead, stop the loop, surface a typed ReauthRequired. Persist a last_auth_error marker as the durable signal (anti-flap: don't re-prompt a healthy box mid-rotation). hermes auth.py:3571-3609, credential_pool.py:1357-1378

At-rest hygiene (steal from hermes)

Atomic writes: O_EXCL + 0o600 to a temp file, fsync, os.replace (symlink-preserving), then fsync the parent dir (0o700). Closes the umask window where tokens briefly sit at 0o644. The "CAS" is identity-compare-then-write under the lock — the file lock is the concurrency control, the refresh-token match is what stops stomping a token another process already advanced. hermes auth.py:1151-1202

05

Three ways to get tokens → models, and the risk that reorders them

The handoff called app-server "the target." The source read holds a caveat serious enough to change the ship order.

The finding that changes the plan

The chatgptAuthTokens app-server mode is stamped internal-use-only in Codex's own source

Verbatim from codex-rs/.../account.rs:87-88: "[UNSTABLE] FOR OPENAI INTERNAL USE ONLY — DO NOT USE. ChatGPT auth tokens are supplied by an external host app and are only stored in memory. Token refresh must be handled by the external host app." It is absent from the public app-server docs (which document 4 of the 7 real AuthMode values). This is exactly the mode our app-server transport is built around. Build against it deliberately, expect churn, and do not make it the default until it's proven — backend-api ships first.

06

The app-server refresh handshake — the one pattern that makes B work

In chatgptAuthTokens mode YOUR store is the source of truth. app-server never refreshes; it asks you after a 401. This is integration-tested in codex-rs end to end, mid-turn.

sequenceDiagram
  participant Host as our transport-appserver
  participant AS as codex app-server
  participant BE as chatgpt backend
  Host->>AS: initialize + initialized
  Host->>AS: account/login/start {chatgptAuthTokens, accessToken, chatgptAccountId}
  Host->>AS: thread/start then turn/start
  AS->>BE: request (Bearer old token)
  BE-->>AS: 401 Unauthorized
  AS->>Host: account/chatgptAuthTokens/refresh {reason: unauthorized}
  Note over Host: refresh against OUR store (10s window)
  Host-->>AS: {accessToken, chatgptAccountId, chatgptPlanType}
  AS->>BE: retry (Bearer new token)
  BE-->>AS: 200 stream
  AS-->>Host: item/* deltas then turn/completed
  • Refresh is host-owned. account/read {refreshToken:true} is a no-op in this mode (proven by test account_read_refresh_token_is_noop_in_external_mode). The only refresh paths are this callback or the host proactively re-calling account/login/start.
  • A failed refresh fails the turn — don't swallow it. codex-rs tests (external_auth_refresh_error_fails_turn) confirm a bad refresh surfaces as a turn error, not a silent retry loop. Our handler's errors must propagate.
  • 10-second window. app-server cancels if the host doesn't answer the refresh request in time — the store's refresh must be fast, not block on a UI prompt.
  • Transport = stdio, newline-delimited JSON (not LSP Content-Length framing), detached child process, agent-scoped CODEX_HOME by default so a product identity never clobbers the user's real ~/.codex. WebSocket is experimental per OpenAI and needs perMessageDeflate:false.
  • Redact tokens from logs with a regex scrubber before any line is written (openclaw's exact three-pattern approach: Bearer tokens, JSON key/value pairs, key=value forms).

10

Decisions I need from you

Three genuine forks. I've marked my recommendation on each — select and queue, or annotate.

1 · Refresh margin — refresh this long before token expiry

Every reference disagrees: loginwithchatgpt 60s, our apps 300s, hermes 120s. Too short risks mid-request expiry; too long wastes refreshes and widens the single-use-token race.

2 · Does transport-appserver land in v0?

It's the genuinely novel, first-of-its-kind piece — but it rides chatgptAuthTokens, which Codex's own source marks "INTERNAL USE ONLY — DO NOT USE." backend-api ships first regardless; this is about whether we publish v0 with app-server too.

3 · WebSocket transport for remote app-server — build it, and which auth?

codex-rs supports two --ws-auth modes: plain capability-token (shared secret, what openclaw ships) and signed-bearer-token (HS256 JWT with exp/nbf/iss/aud). WS is OpenAI-experimental. Needed only for a remote/cloud-hosted app-server.

Standing risk — decided posture accepted

Impersonating the Codex CLI to power non-Codex products is unofficial and gray-area; worst when a hosted app pools one subscription. Decision: OpenAI has been welcoming so far, so we proceed — and retire the project the moment they signal otherwise. The mitigations stay in regardless because they're also just good engineering: OAuth is personal/self-host only and never the multi-tenant default, never pool tokens, keep an API-key/Ollama fallback, honest experimental README. The kill-switch and quarantine machinery double as the retire-cleanly path if the posture flips. (Engineering guidance, not legal advice.)
