Architecture Consensus · Decision Memo

Tapping the ChatGPT subscription, the right way

Let people sign in with their own ChatGPT account and run OpenAI models on their subscription — securely, across web, React Native, and native iOS. The decision: build a best-in-class, cross-platform SDK for it.

reviewers: Codex · Grok · Fable apps audited: ai-finances · calorie-tracking · music-player reference impls: openclaw · hermes-agent · 2 OSS libs
The verdict

Build it — a best-in-class, cross-platform subscription-AI SDK. The bar isn’t novelty, it’s better, cleaner, more honest than anything shipped.

“Someone already built it” is a weak veto. What exists is fragmented: EvanZhou is web-only behind a browser extension, ben-vargas is a Node/CLI shim, openclaw and hermes have the best engineering but welded inside a 27k-file agent OS and a Python monolith — you can’t npm i either. The clean web + React Native + Swift trifecta, with app-server as a first-class transport, does not exist. That gap is the reason to build.

Keep the reviewers’ discipline as guardrails, not as a veto: stay small and focused — a core plus thin adapters, never a gateway — and bake correctness into the API shape so misuse is impossible. The one non-negotiable, and the bug already shipped in ai-finances: one ChatGPT identity ↔ one app user. The global CHATGPT_OAUTH_TOKENS_B64 seed pools your account for every visitor.

01

Where “better” actually lives

Not novelty — the existing tools are fragmented and single-platform. Four places a from-scratch build wins outright.

CROSS-PLATFORM the moat

One core, three real adapters

Web + React Native + Swift from a single lifecycle core. Everyone else picked one platform — the trifecta is unbuilt, and it’s the hardest part to copy.

APP-SERVER FIRST

The documented path as the headline

Lead with codex app-server; keep backend-api as the legacy fallback. The others bury or omit the supported transport — you’d ship it as the default.

SAFE BY SHAPE

Misuse is impossible, not discouraged

Subject derived server-side, compare-and-swap tokens, a quarantine state machine — baked into the types. The existing libs leave these to the caller, and callers get them wrong (your own apps did).

HONEST BY DEFAULT

The version a careful dev trusts

Kill-switch, API-key / Ollama fallback, and personal / self-host framing wired in as first-class — not a README disclaimer. Being the most honest one is itself a differentiator.

WHERE NOT TO COMPETE

Don’t out-polish EvanZhou’s browser-extension custody on web — that’s his strength. Adopt it as your web adapter and spend the effort on the React Native + Swift + app-server story nobody else has. Win on breadth, not on his home turf. The one thing polish can’t change: the foundation still rides the Codex OAuth client to broker a subscription — a cleaner library doesn’t alter the ToS posture, which is exactly why “honest by default” is a feature, not a footnote.

02

Three ways to get the tokens to the models

Every implementation reviewed is a variation on one of these. They differ in who holds the tokens and how fragile the wire is.

OPTION A fragile

Direct backend-api

Reuse Codex CLI’s client_id, POST straight to chatgpt.com/backend-api/codex/responses with originator: codex_cli_rs headers. What all 3 of your apps do now. Impersonates the CLI at the wire — one header change breaks everything. Fine for personal / mobile where no binary can run.

OPTION B target

codex app-server

Run OpenAI’s own binary; drive it over JSON-RPC. Officially documented, three auth modes (chatgpt, chatgptDeviceCode, chatgptAuthTokens). Codex owns protocol drift + refresh for you. This is the tweet’s method — done properly. Needs a host that can run the binary.

OPTION C web only

Extension token custody

EvanZhou v2: an open-source browser extension holds the tokens; your server calls per-request and stores no user tokens at all. The safest multi-user web pattern — CORS blocks direct browser calls, the extension bridges. Chrome/Firefox only, web only.

04

What the three reviewers said

Independent passes — my own file-level audit that cloned all four repos, plus Codex (gpt-5.6) and Grok reasoning from the verified findings.

Grok effort: high

  • No product lib. Extract @vish/codex-auth: core + web/rn/ios TokenStore adapters + two transports.
  • Copy openclaw’s shape (provider ≠ auth profile ≠ runtime), steal hermes token hygiene, use EvanZhou as web-UX reference only.
  • Biggest landmine: impersonation + token pooling — fix per-user isolation first.

Fable file-level audit

  • All 3 apps + both OSS libs reuse Codex’s client_id and hit backend-api/codex — verified line-by-line.
  • openclaw spawns the real binary (app-server, chatgptAuthTokens); hermes ships both paths as a runtime switch.
  • ai-finances stores tokens base64, not encrypted, in one global row. Fix before any multi-user ship.

Codex gpt-5.6, effort high

  • Adopt app-server as the boundary; build only the seam — a private BFF gateway + typed client SDKs, not another OAuth product.
  • Clients never submit a userId/account-id/bearer — the gateway derives the subject from the app session. Versioned tokens + compare-and-swap kills the refresh race.
  • Strongest isolation: one CODEX_HOME / process per user for remote app-server. Get written OpenAI approval before any commercial multi-tenant launch.
Their caution → our guardrails

Building doesn’t discard their discipline — it inherits it. Stay small (core + thin adapters, not a gateway). Inference on app-server wherever a binary runs. Per-user isolation is mandatory and structural, not a convention. Ship as a personal / self-host feature with API-key / Ollama always wired as fallback.

06

Login, expiry & refresh — the lifecycle

Same shape across every implementation. Under app-server Codex does most of this for you; under backend-api you own it.

1Login — PKCE (S256) against auth.openai.com/oauth/authorize. Mobile: ASWebAuthenticationSession. Web multi-user: the extension. Validate state for CSRF.
2Access token — short-lived JWT, ~1h TTL. Store per user, encrypted (Keychain / SecureStore / AES-GCM DB row) — never bare base64, never a global key.
3Refresh — lazy, at expiry − 5min, plus a reactive 401→refresh→retry. Singleflight mutex so concurrent calls share one refresh, and compare-and-swap the rotated token by version so two refreshers can’t clobber each other.
4Quarantine — on invalid_grant / revoke-class 4xx, mark the refresh dead, stop the loop, surface typed ReauthRequired. (hermes’ best pattern; missing in all 3 of your apps.)
5Logout — always delete local tokens; on app-server call account/logout. No reliable public revoke for the CLI client → tell the user to revoke in their OpenAI account UI.

The chatgptAuthTokens ownership flip: in that mode your TokenStore is the source of truth — you did the PKCE, you hold + refresh the token, and app-server asks you for a fresh access token after auth errors. Don’t dual-write into both your DB and the Codex home. The chatgpt_account_id from the JWT is unverified routing metadata — send it as a header, never trust it for your app’s authorization.

07

The single biggest risk

Technical + legal, same root

Impersonating the Codex CLI to power non-Codex products — worst when a hosted app pools or brokers one subscription.

ToS: the community libraries are explicit — unofficial, credentials are passwords, do not pool or share tokens, you own compliance, OpenAI can disable it at any time. OpenAI’s docs bless embedding Codex; they do not license reselling ChatGPT access as your SaaS backend. Technical: one originator check or client_id rotation kills all three apps at once — no SLA. Blast radius: ai-finances’ global token means every visitor burns your quota and one DB leak exposes your bearer.

CONCRETE FAILURE  With today’s single global row, Bob signing in overwrites Vish’s bearer + account-id. Vish’s next app-authorized request then runs against Bob’s subscription — while two refreshers race on one rotated token. Per-user records + server-derived subject + isolated app-server state + single-flight-CAS refresh removes all of it.

Mitigations, by leverage: (1) OAuth = personal / self-host only, never the multi-tenant default; (2) never pool — per-user stores, or store nothing (C); (3) move inference to app-server so you’re on a documented protocol; (4) honest experimental UX + README; (5) encrypt at rest, quarantine, logout clears; (6) always keep API-key / Ollama fallback so a clamp is degraded mode, not an outage. Before any commercial multi-tenant launch: get written OpenAI approval for the exact per-user hosted flow.

08

The build — v0 and the shape

A small monorepo, Codex-specific: a core plus thin adapters. The auth client is never the inference client.

V0 SCOPE ship first

core + web adapter + app-server transport, dogfooded end-to-end on ai-finances — with ripping out the CHATGPT_OAUTH_TOKENS_B64 global seed as the first visible win. Then add the React Native and Swift adapters once the core is proven in a repo you already run.

// @vish/codex-auth — token lifecycle only, inference is a separate transport
// subject is derived server-side from the app session — clients NEVER submit
// a userId, chatgpt-account-id, or bearer. That's what makes pooling impossible.
interface CredentialStore { load(subject); compareAndSwap(subject, version, next); delete(subject) }
interface CodexAuthClient  { beginLogin; completeLogin; getAccessToken; logout; status }
interface RuntimeTransport { connect(subject): SubscriptionAI }   // AppServer | BackendApi

packages/
  core                PKCE · device-code · refresh singleflight · quarantine · JWT parse
  store-web           encrypted DB row, keyed by server-derived subject (never global)
  store-react-native  expo-secure-store
  store-ios           Keychain, ThisDeviceOnly (Swift port)
  transport-appserver JSON-RPC to codex binary — the target path
  transport-backendapidirect /codex/responses — mobile, behind a kill-switch
  • Core owns lifecycle, not transport. One refresh implementation, one quarantine state machine, shared by every app.
  • The API forces a server-derived subject. No client-submitted userId / bearer exists in the surface — pooling is structurally impossible, not merely discouraged.
  • Two transports behind one interface. app-server is the default; backend-api is the flagged fallback for mobile — flip per platform without touching app code, never a silent downgrade.
  • Reference, don’t depend. Adopt EvanZhou’s extension as the web adapter; copy openclaw’s separation and hermes’ hygiene. Keep the lib ~2k lines, not a gateway.
